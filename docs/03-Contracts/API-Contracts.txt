02. COMMON API STANDARDS
========================
Base URL local: http://localhost:8080. Public demo: HTTPS ngrok URL được cấp thực tế (không hardcode).
Public resource paths: /api/v1/{service}/...; internal: /internal/v1/... (private Docker DNS). Đây là chuẩn mới thay tên /internal/... sơ bộ; update diagrams nếu có path cũ.
Serialization: JSON UTF-8 camelCase cho API, UTC RFC3339 timestamps (vd 2026-11-19T12:00:00Z), UUID canonical, money/quantity integer. ZaloPay giữ nguyên snake_case. JSON int64 cho Gem/VND; client JS phải dùng safe-integer range hoặc parser hỗ trợ int64, không dùng float tính tiền. C# long, checked arithmetic. Role/enum strings đúng casing trong schema. Dữ liệu nullable có thể trả null; không tự bỏ field bắt buộc. Request field ngoài schema reject/ignore nhất quán theo team; không bind trực tiếp entity.
Success: trả DTO trực tiếp, không dùng wrapper success/data; collection dùng {items, page, pageSize, totalCount}; page 1-based, mặc định 20, tối đa 100; from/to timestamp [from,to); ngày analytics from/to [from,to), tối đa 31 ngày mặc định; sort ổn định với ID tie-break. Trim q <=100, reason <=500, validate enum/UUID, minPrice<=maxPrice. 204 không body; 201/202 kèm Location khi có resource/status URI. 202 chỉ khi intent/operation đã persist, không đồng nghĩa thành công.
Headers: Authorization: Bearer <accessToken>; Content-Type: application/json (body); Accept: application/json; X-Correlation-ID UUID optional, generate nếu absent; echo correlation ID trên response và propagate internal. Idempotency-Key required ở những endpoint có ghi rõ; 1..128 ký tự opaque, khuyến nghị UUID. Scope key theo actor + operation + resource/body fingerprint; replay exact returns existing resource/result, khác payload => 409; không xử lý side effect lần hai. Persist key cùng local state, không chỉ Redis. Không tự sinh key mới khi retry timeout; không dùng idempotency key làm auth token.
Error format: application/problem+json (ProblemDetails). Ví dụ: {"type":"about:blank","title":"Conflict","status":409,"detail":"Listing is not active.","instance":"/api/v1/marketplace/listings/11111111-1111-4111-8111-111111111111/purchase","code":"LISTING_NOT_ACTIVE","traceId":"trace-example"}. Không lộ stack, database, token. 400 validation; 401 token/credentials; 403 role/status; 404 missing hoặc không sở hữu resource; 409 state/idempotency conflict; 422 rule giá/giá trị; 429 throttle; 500 lỗi ngoài dự kiến; 502 provider rejection; 503 dependency lỗi/unknown trước durable acceptance. Callback ZaloPay là ngoại lệ: provider acknowledgement JSON.

03. AUTHORIZATION / SERVICE BOUNDARIES
=====================================
Auth phát internal JWT sub=userId, role=Player|GM|CS, iss, aud, exp, iat, jti; role từ AuthDb. TTL đề xuất access 15 phút / refresh 7 ngày; rotate refresh hash, revoke logout; không log token. GM/CS preseed; Google JIT user luôn Player. /auth/login dành seeded password accounts; cần thêm PasswordHash nullable và DisplayName nếu ERD AuthDb chưa có (hoặc thống nhất Google-only rồi bỏ login endpoint). Password hash chuẩn ASP.NET Core Identity/PasswordHasher, không plaintext. Không auto-link Google account bằng email; pre-link bằng verified subject qua admin seed; email conflict cần xử lý thủ công.
Gateway xác minh JWT và policy cho public protected routes; kiểm tra account status qua Auth internal (fail closed khi không xác minh được), tránh vòng lặp khi gọi Auth public login; Auth xử lý ban ở login/refresh/me. Services cũng verify JWT signature/iss/aud/exp và quyền ownership; không tin X-User-Id/role từ client. Banned bị chặn toàn bộ protected routes; TradeRestricted chặn create/purchase mới, vẫn xem, hủy listing của mình, nạp Gem theo phương án này; Saga đã accept vẫn chạy tới kết quả. Không hủy Saga khi JWT hết hạn. Buyer/Seller là vai trò trong nghiệp vụ, không có role JWT riêng.
Internal calls: private network + X-Service-Key riêng từng caller, mapping caller/scopes trên service đích; constant-time compare, không forward key client, không public internal routes, rotate secret và local TLS nếu có; MVP HTTP trong Docker, production cần mTLS/service identity. Service key và JWT không phải một loại credential. Auth status routes chỉ caller được phép; Admin chỉ CS có thể gọi moderation; Seeder credential riêng. Không sử dụng shared universal key. RabbitMQ account credentials, queue/exchange ACL riêng khi khả thi.
Gateway allowlist theo method/path ở danh mục dưới, không wildcard /internal. /auth/login, /auth/google, /auth/refresh, /auth/logout và /wallet/zalopay/callback không require access JWT (logout dùng refresh token, callback MAC). Rate limit login/topup/purchase; không dùng rate limit người chơi cho provider callback. /metrics, /health/live, /health/ready, Swagger nội bộ không public qua ngrok. Public API docs có thể xem localhost.
Internal service DNS: http://auth-api:8080, wallet-api:8080, inventory-api:8080, marketplace-api:8080, admin-api:8080. Gateway route không đổi prefix; service nhận đúng path. Tất cả ports đề xuất, cập nhật theo compose. Ngrok chỉ forward allowlist gateway.

===================================================
Ký hiệu body — là không có request body; DTO được định nghĩa ở mục 05. Access Service:* là internal credential, không phải JWT role. Điểm quan trọng: API IDs dưới đây là IDs mới, FR IDs vẫn giữ gốc (AUTH-03 API != FR-AUTH-03 OTP đã cắt).

06. ZALOPAY / GOOGLE INTEGRATION CONTRACTS
==========================================
ZaloPay v2 Sandbox base: https://sb-openapi.zalopay.vn; wallet holds app_id, Key1, Key2, callback URL in secret/config, never in source or client. Provider contract reference: https://developers.zalopay.vn/v2/general/overview.html (checked 2026-11-19). Use classic v2 gateway contract, do not mix callback codes with a different ZaloPay API version.
Create order: POST /v2/create, application/x-www-form-urlencoded. app_id:int, app_trans_id:string unique (yyMMdd prefix in Vietnam time + unique suffix within provider length), app_user:string (internal userId), app_time:int64 Unix ms, amount:int64 VND, item:string JSON array, embed_data:string JSON object, description:string, callback_url:HTTPS URL, bank_code:string as configured by sandbox, mac:string hex. Compute HMAC-SHA256 Key1 over pipe-joined app_id, app_trans_id, app_user, amount, app_time, embed_data, item in this order; use exact serialized strings. Response: return_code, return_message, sub_return_code, sub_return_message, order_url, zp_trans_token (if returned). Persist paymentUrl, not provider secret. return_code=1 + URL means order created, not paid. Duplicate app_trans_id (sub_return_code=-68) or network timeout => reconcile original order; no second charge/order by blind retry.
Callback: POST /api/v1/wallet/zalopay/callback, JSON data:string, mac:string, type:int=1. Verify HMAC-SHA256(Key2, original data string) constant-time before parsing inner data. Validate configured app_id, app_trans_id, app_user, amount, zp_trans_id; compare to original persisted order, not client. For mismatched valid signed data, flag for review and do not credit; reply 0 while unresolved, reconcile and alert. Exact duplicate of already credited payment -> 2; conflicting transaction ID is not an exact duplicate. First successful durable credit -> 1; transient DB failure -> 0; invalid MAC/unsupported type -> -1. HTTP 200 with {return_code,return_message}; callback malformed JSON -> 400 as documented in WAL-06. No JWT, no dependence on redirect.
Query: POST /v2/query, app_id, app_trans_id, mac=HMAC-SHA256(Key1, app_id|app_trans_id|Key1). Response return_code 1=success, 2=failure, 3=unpaid/processing; also use sub_return_code and is_processing. On successful result validate amount and zp_trans_id and use same settlement operation as callback. Query pending orders periodically and around expiry (default provider window 15 min); mark Failed/Expired only on confirmed terminal provider result. Network errors/uncertain expiry remain Pending, log for review; a verified late payment must be reconciled, never silently dropped. Sandbox config/credential and exact expiry settings must be tested. No ZaloPay refund endpoint in MVP: Saga refund is release of virtual Gem hold only.
SQL settlement: lock persisted order, verify existing credit/unique provider ID, increase Wallet.TotalBalance by stored GemAmount, add one TopUp ledger entry with OperationKey=topup:{topUpId}, update Paid + ProviderTxnId + PaidAt, commit atomically. Use unique indexes on appTransId, providerTxnId (filtered where not NULL) and OperationKey. Callback/query may run concurrently. Pending order has nullable paymentUrl; persist it when create succeeds. Add PaymentUrl nullable to ERD 09 if missing. Never overwrite Paid with Failed/Pending. Provider redirect only opens status page; GET top-up status uses SQL.
Google: client obtains Google ID credential via Google Identity Services (minimal local browser test page). POST /api/v1/auth/google with {idToken}; Auth verifies signature, issuer, audience against configured OAuth client ID, expiry, and nonce only if a server-generated nonce challenge is implemented (otherwise omit optional nonce). If Google GIS posts directly to backend, use its matching CSRF validation or adapt via explicit client JSON callback; protect login against CSRF as appropriate. Use stable Google sub + issuer for identity, not email; verify email when used; unique provider+subject. Return internal JWT, never authorize marketplace by Google token. Official guide: https://developers.google.com/identity/gsi/web/guides/verify-google-id-token. No Google access token storage or extra scopes in MVP.

07. ASYNCHRONOUS MESSAGE CONTRACTS (RABBITMQ / MASSTRANSIT)
==========================================================
Shared project: Marketplace.Contracts.V1 (C# records). All services reference same version. One logical type per command/event; don't duplicate differing types by service namespace. Commands sent to destination queue; events published; MassTransit native envelope, no second custom JSON envelope. Common business payload fields: correlationId:uuid (=tradeId for trade, listingId for listing lifecycle); operationId:uuid (stable for each logical command/result; deterministically generated or persisted); occurredAt:UTC dt (events only). Use MassTransit MessageId, CorrelationId, Causation/InitiatorId headers as applicable. Retry same operationId; result event echoes operationId and correlationId. All fields required unless '?'; long = signed Int64; positive money nonnegative as defined above. Names are case sensitive in shared C# code and serialized camelCase. No JWT, raw passwords, provider secrets or whole entities in messages.
Queue names proposed: wallet-commands, inventory-commands, marketplace-saga, marketplace-projection, admin-analytics. Durable queues/persistent messages, broker volumes. Commands have one owning consumer; events may have multiple independent consumers.

08. WORKFLOW STATE AND BUSINESS INVARIANTS
==========================================
Listing: PendingLock -> Active or CreateFailed; Active -> Processing or Cancelled; Processing -> Sold or Active after compensation. Never reactivate cancelled/sold. Redis SET NX PX token (TTL proposed 20s), compare-and-delete; same lock key for cancel/purchase where used. SQL conditional UPDATE WHERE state=Active plus version (only one claim); persist trade+saga+outbox in same transaction; release Redis after durable claim, not after the entire Saga. Redis unavailable => fail closed 503 before intent. Active only after lock confirmed. Lock/create failures with unknown result -> PendingLock and recovery via same listingId; only fail after confirmed no lock or compensated release. Cancel commit + unlock command in outbox; inventory unlock retries; cancel API reports Pending until confirmed. If item is PendingSettlement cannot unlock casually.
Trade state machine: HoldingFunds -> Transferring -> Settling -> Finalizing -> Completed. Hold rejection -> Failed + Listing Active. Confirmed transfer rejection -> ReleasingFunds -> Failed + Listing Active. Confirmed settlement rejection -> ReversingItem -> ReleasingFunds -> Failed + Listing Active. Unknown outcome stays in current state, requiresReview if exhausted; never assume timeout means rejection. After settle commit, forward recovery only. Complete only after finalization confirmed; publish TradeCompletedEvent from same commit as Sold/Completed. Authoritative trace GET from owning service.
Wallet: Total >= Hold >= 0, Available=Total-Hold. Hold atomically increments Hold after checking available. Settle verifies hold amount/owner/status, debits Buyer total and hold, credits Seller net, burn fee; one WalletDb tx (deterministic row lock order). FundHold state Held -> Settled or Released; Settled must never release. Ledger deltas Hold: total 0/hold +gross; Release: total 0/hold -gross; SettlementDebit: total -gross/hold -gross; SettlementCredit: total +net/hold 0. TaxBurn is audit-only recorded under sellerId (totalDelta=0, holdDelta=0, feeGem=fee), never subtract fee again. Supply falls exactly fee. Unique OperationKey per trade+operation+party; same replay no mutation. Buyer/seller wallets initialized lazily idempotently.
Inventory: one item/stack per listing, whole stack purchased; item remains same itemId when ownership changes, PendingSettlement blocked from use/listing. Reserve seller slot until finalize to guarantee reverse capacity. Transfer checks locked item/listing/owner/quantity, buyer capacity; local atomic owner change + transfer record. Reverse restores seller locked state with same listingId; finalize makes Available and releases reserved slot. Replay exact operation returns prior outcome. Grant and lock capacity/ownership protected with SQL state/row version.
Price: Gem integer, quantity positive; gross=checked(unitPrice*quantity); fee=floor(gross*feeBps/10000) using checked wider intermediate; sellerNet=gross-fee. Proposed feeBps=500 (5%), bandBps=2000 (20%). Min=max(1,ceil(reference*(10000-band)/10000)); max=floor(reference*(10000+band)/10000). Validate current price at create only; price changes do not invalidate old listings by default; capture policy version, fee and amounts in Trade/Listing snapshot; no client total/fee authority. Admin owns PricePolicy SQL + Redis versioned projection. Redis key price:policy:{templateId}; Admin single writer; Marketplace read-only. On cache miss, Marketplace falls back to internal REST ADM-I01 (Admin refreshes Redis from SQL); if policy is still missing (404) or Admin unavailable, reject MKT-01 with 503 PRICE_POLICY_UNAVAILABLE rather than default silently; Admin warms up cache on startup. Seed base prices per template. Daily weighted avg = floor(sum grossGem / sum quantity), at least 1; use BasePrice until first successful trade, choose current Vietnam business day average once data available, otherwise carry previous reference. Persist Trade_Facts unique tradeId; derive Redis per-day aggregates from durable facts or idempotent projection; include late events in event day, reconcile after midnight. Summary job 00:00 Asia/Ho_Chi_Minh upserts prior day, no destructive reset of in-flight data. Price policy config version increments on GM modifications; reference updates use monotonic projection version or timestamp to avoid stale overwrite. Supply is stock, turnover is volume, neither alone proves inflation.

T11 Integration: Docker compose up, private routes inaccessible via Gateway, /metrics scraped, no secrets in logs; verify ProblemDetails codes, paging, ownership for all endpoints.
